# setup-springboot3x-resilience4j

Step-by-step guide to build and run a Spring Boot 3.4 middleware (Component B) with Resilience4j retry + circuit breaker. Receives JSON from upstream, generates `airway_bill_id`, and forwards enriched JSON to Component C with fault tolerance.

## Tech Stack

| Component | Confirmed Version |
|---|---|
| Spring Boot | 3.4.5 |
| Resilience4j | 2.2.0 |
| Java | OpenJDK 17.0.18 LTS |
| Maven | 3.6.3 |
| Port | 8082 |
| Service name | jek-otel-java-springboot3x-r4j |
| Fault injection | 20% on all endpoints except /health |
| Retry | 3 attempts, 500ms exponential backoff to Component C |
| Circuit breaker | Sliding window 10, 50% failure threshold, 10s open |

## What it does

```
JSON in (from Component A)
  → Generate airway_bill_id (simulates freight forwarder assigning Master AWB)
  → Append airway_bill_id to payload
  → Forward enriched JSON to Component C at localhost:8083/jek-process
     ├── Success: return Component C's response (XML from D)
     ├── Retry: if C returns 500, retry up to 3 times with backoff
     └── Fallback: if all retries fail or circuit breaker opens, return cached response
```

## Prerequisites

- EC2 instance with Java 17 and Maven (from `setup-ec2-centos9`)
- Component C running on port 8083 (from `setup-springboot3x-apachecamel`)
- Component D running on port 8084 (from `setup-springboot3x`)
- SSH access: `ssh -i ~/.ssh/jek_rsa_pem ec2-user@<EC2_PUBLIC_IP>`

## Step 0: Verify Components C and D are running

```bash
curl -sf http://localhost:8083/health && echo " — Component C OK"
curl -sf http://localhost:8084/health && echo " — Component D OK"
```

Both must return healthy before starting Component B.

## Step 1: Copy source to EC2

From your local machine (in the `setup-springboot3x-resilience4j` skill directory):

```bash
ssh -i ~/.ssh/jek_rsa_pem ec2-user@<EC2_PUBLIC_IP> \
  'sudo mkdir -p /opt/cargostream/component-b && sudo chown ec2-user:ec2-user /opt/cargostream/component-b'

scp -i ~/.ssh/jek_rsa_pem -r references/* ec2-user@<EC2_PUBLIC_IP>:/opt/cargostream/component-b/
```

## Step 2: Build with Maven

```bash
ssh -i ~/.ssh/jek_rsa_pem ec2-user@<EC2_PUBLIC_IP>

cd /opt/cargostream/component-b
mvn clean package -DskipTests
```

This produces `target/springboot3x-r4j-0.0.1-SNAPSHOT.jar`.

## Step 3: Run the application

If `JAVA_TOOL_OPTIONS` is set (from `springboot3x-otel-java-tool-opt`), the OTel agent AND extensions load automatically — no `-javaagent` needed. Ensure JAVA_TOOL_OPTIONS includes the full flags (agent + DSM extension + loader.path + header capture). See the `springboot3x-otel-java-tool-opt` skill for the complete configuration.

**Where does `transaction_id` appear in span attributes?**
- On **Component D**: extracted from the XML body by the XML attribute extractor extension (loaded via `-Dloader.path`)
- On **Components B and C**: captured from the HTTP request header via `-Dotel.instrumentation.http.server.capture-request-headers=transaction_id`
- For this to work, the caller must send `transaction_id` as an **HTTP header** (in addition to the JSON body)

```bash
cd /opt/cargostream/component-b
java -jar target/springboot3x-r4j-0.0.1-SNAPSHOT.jar
```

Or in the background:

```bash
nohup java -jar target/springboot3x-r4j-0.0.1-SNAPSHOT.jar > /tmp/component-b.log 2>&1 &
sleep 15
curl -s http://localhost:8082/health
```

On startup you should see:

```
Picked up JAVA_TOOL_OPTIONS: -javaagent:/opt/otel/opentelemetry-javaagent.jar ...
[otel.javaagent] opentelemetry-javaagent - version: 2.26.1
Started Springboot3xR4jApplication in X.XX seconds
```

## Step 4: Verify

### 4a. Health check

```bash
curl -s http://localhost:8082/health
```

Expected: `{"status":"healthy","service":"jek-otel-java-springboot3x-r4j","port":8082}`

### 4b. Test B → C → D chain

```bash
curl -X POST http://localhost:8082/jek-forward \
  -H "Content-Type: application/json" \
  -d '{"transaction_id": "test-tx-001", "timestamp": "2026-04-14T10:00:00Z", "source": "manual-test"}'
```

Expected: XML response from Component D containing `houseway_bill_id` (generated by C) and `airway_bill_id` (generated by B).

### 4c. Verify Resilience4j retries

Send 20+ requests — some will hit C's 20% fault injection, triggering retries:

```bash
for i in $(seq 1 20); do
  CODE=$(curl -s -o /dev/null -w "%{http_code}" -X POST http://localhost:8082/jek-forward \
    -H "Content-Type: application/json" \
    -d "{\"transaction_id\": \"tx-$i\", \"timestamp\": \"2026-04-14T10:00:00Z\", \"source\": \"test\"}")
  echo "Request $i: HTTP $CODE"
done
```

Check logs for retry activity:

```bash
grep -E "Calling Component C|Fallback triggered|retry" /tmp/component-b.log | tail -10
```

### 4d. Verify in Datadog APM (if JAVA_TOOL_OPTIONS is set)

Go to **APM > Traces**. Search for `service:jek-otel-java-springboot3x-r4j`.

You should see:
- Incoming span for POST `/jek-forward`
- Outgoing HTTP span to Component C at `localhost:8083/jek-process`
- **Distributed trace B → C → D** with all 3 services linked
- On retries: multiple outgoing HTTP spans under the same parent span
- Fallback responses when circuit breaker opens

## Troubleshooting

| Issue | Fix |
|---|---|
| Port 8082 in use | `pkill -f springboot3x-r4j` |
| Component C not reachable | Verify C is running: `curl http://localhost:8083/health` |
| All requests return fallback | Circuit breaker may be open. Wait 10s for half-open transition. |
| No OTel traces | Check `JAVA_TOOL_OPTIONS` is set: `echo $JAVA_TOOL_OPTIONS` |

## Teardown

```bash
pkill -f springboot3x-r4j 2>/dev/null
rm -rf /opt/cargostream/component-b
```
